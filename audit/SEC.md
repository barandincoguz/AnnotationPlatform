| SEC-1 | High | mirror/neon_client | `table_name` and column names from `payload.keys()` are interpolated unquoted into Postgres SQL identifiers (`baran_{table}`, `{col_list}`, `{set_clause}`, `ON CONFLICT ({pk_cols})`). Values are schema-derived (SQLite trigger `json_object()` keys = literal column names) so the attack surface requires an adversary with write access to `_outbox` or the ability to corrupt the trigger-generated column names — not reachable from any HTTP path today. However there is no `psycopg.sql.Identifier` quoting, so a column name containing `"` or `;` would produce broken/injectable SQL against Neon Postgres. | `backend/mirror/neon_client.py:96, 181, 184–186, 192, 203–204` | APPLY-W2.5 — wrap identifiers with `psycopg.sql.Identifier`/`psycopg.sql.SQL` |
| SEC-2 | Medium | mirror/neon_client | `NeonClient.connect` logs `log.warning("NeonClient.connect failed: %s", exc)` where `exc` is a `psycopg.OperationalError`. On some psycopg3 builds the exception string includes the DSN (host, user, database but not typically the password). If it does, the NEON_MIRROR_URL credential is written to the application log at WARNING level. | `backend/mirror/neon_client.py:76` | APPLY-W2 — log `type(exc).__name__` + a stripped message, never `exc` directly |
| SEC-3 | Medium | secrets | `.env.production` is gitignored and not committed, but it ships on disk with `BOOTSTRAP_ADMIN_USERNAME=admin` and `BOOTSTRAP_ADMIN_PASSWORD=admin123456789` as live values (not just placeholders). The placeholder-blocker in `prod_enforce.py` (`_PLACEHOLDER_PASSWORD_PATTERNS`) correctly catches `"admin"` substring and would refuse to start — so the credential cannot be used in production without triggering a boot-time error. The risk is: an operator copies the file verbatim, changes `ENVIRONMENT=production`, and sees a boot failure that they "fix" by weakening or removing the check rather than rotating the password. The file itself should not ship with a real username/password pair, even one that fails the production gate. | `.env.production:11-12` | APPLY-W2 — replace `admin` / `admin123456789` with `<REPLACE_ME>` placeholders matching `.env.example` |

| SEC-5 | Medium | csrf | `OriginCheckMiddleware` is explicitly bypassed for `ENVIRONMENT != "production"` (development and test). The residual risk is: if a staging deploy is set `ENVIRONMENT=development` (common mistake), CSRF protection is silently absent. There is no `staging` environment value that would enable the check. | `backend/shared/csrf.py:56-58` | APPLY-W2 — add `ENVIRONMENT=staging` as a third production-like value that enables the check; or emit a startup warning when `ENVIRONMENT` is `development` but `ALLOWED_ORIGINS` is set |
| SEC-6 | Low | brute-force | Rate limiter is in-memory, per-IP, single-process only. Comment in `rate_limit.py` and `users/routes.py` both document this. In a multi-worker or multi-container deployment the per-IP window is per-worker, multiplying effective budget by worker count. Login: 10 hits / 5 min × N workers = N × 10 before any 429. No current horizontal-scale deployment, but worth flagging for the Phase 5 "production hardening" pass. | `backend/shared/rate_limit.py:1-17` `backend/users/routes.py:29-38` | DEFER — in-scope for Phase 5 only if horizontal scale is planned; Redis-backed limiter exceeds current scope |
| SEC-7 | Low | brute-force | `/api/auth/logout` (`POST`) has no rate limit. Not a DoS risk given SQLite single-writer, but could pollute access logs. | `backend/users/routes.py:115-125` | DEFER — logout is idempotent + cheap; no practical blast radius |
| SEC-8 | Low | mirror/config | `NEON_MIRROR_URL` is read at module import time into a module-level variable.
