# D3 Frontend Logic Audit (static) — 2026-05-23

## Headline finding

| ID | Sev | Description |
|----|-----|-------------|
| FE-1 | High | jsdom/undici AbortSignal cross-realm incompatibility breaks 34 vitest tests. Root cause: `vite.config.ts` sets `environment: 'jsdom'`; openapi-fetch (~0.13) passes an `AbortSignal` from the undici realm into jsdom's `fetch`, which fails the `instanceof AbortSignal` realm check. Affects every test file that exercises a hook or component that calls the typed API client (`client.GET/POST/PUT/DELETE`). Affected files (representative — all 96 test files share the same MSW+openapi-fetch stack, so any test that triggers a real `client.*` call is vulnerable): `src/hooks/useLock.test.tsx`, `src/hooks/useDraft.test.tsx`, `src/hooks/useSSE.test.tsx`, `src/routes/AnnotateDoc.test.tsx`, `src/api/client.test.ts`, `src/api/queries/auth.test.tsx`, `src/routes/Login.test.tsx`. Proposed direction: add `environmentOptions: { customExportConditions: ['...'] }` and pin `pool: 'forks'` with `poolOptions.forks.execArgv: ['--experimental-vm-modules']`, OR switch `environment` to `'happy-dom'` which uses the same realm as vitest's own fetch shim and avoids the undici cross-realm split entirely. |

| FE-2 | Medium | useLock — heartbeat | Heartbeat POST has no `AbortController` / `signal`. When the interval fires after `cancelledRef.current = true` (i.e. the guard check passes) but before the `await` resolves, the response handler still runs and can call `setSnapshot` on an unmounted component. The `cancelledRef.current` guard at line 100 catches this correctly for the state update, but the outstanding `fetch` itself is never cancelled, leaving a dangling in-flight request on every lock release / route change. Low blast radius because the server ignores the call, but it accumulates across navigations. | `src/hooks/useLock.ts:85-107` | Low-risk leak; add `signal: acquireCtrl.signal` to the heartbeat call (reuse the same controller, which is already aborted on cleanup). |
| FE-3 | Medium | useLock — release() race | The exported `release()` callback (line 153) does not set `cancelledRef.current = true` before awaiting the release POST. If the effect cleanup runs concurrently (e.g. React strict-mode double-invoke, or a route change racing a manual release), both the cleanup `fetch` (keepalive beacon) and the mutation `client.POST` fire at the same time. The server is idempotent on double-release (404 is tolerated), so this is harmless in practice, but the heartbeat timer is cleared in `release()` without checking `cancelledRef`, meaning a tight race can leave the heartbeat running after `release()` returns if the timer fires between the `clearInterval` and the `await`. | `src/hooks/useLock.ts:153-172` | Low severity; set `cancelledRef.current = true` at the top of `release()`. |
| FE-4 | Medium | useSSE — no reconnect back-off | `useSSE` creates a new `EventSource('/api/events')` on every mount and never replaces it on error — the browser's native SSE reconnect is relied upon (correct), but the `onerror` handler (line 32) invalidates `feedKeys.all` + `usersKeys.online()` on every `CONNECTING` state transition. A flaky network or a temporarily unavailable backend triggers repeated `qc.invalidateQueries` calls in tight succession, each spawning a refetch of every mounted feed tab query. Under normal reconnect timing (1–5 s browser back-off) this is tolerable, but it is an unthrottled invalidation storm with no debounce or max-rate guard. | `src/hooks/useSSE.ts:32-39` | Observation; no data loss. Could add a `Date.now()` gate to suppress duplicate invalidations within a 2-second window. |

However, `acquiringRef` is a stable ref (not reactive), so the lock handler correctly reads the latest `acquiringDocId` without causing re-registration. No bug, but the comment at line 21 (`acquiringRef.current = opts.acquiringDocId`) documents this intent — worth a test assertion. | `src/hooks/useSSE.ts:20-21` | Info — intentional and safe. |
| FE-6 | Low | lockHandlers — raw string key `['feed']` | `lockHandlers.ts` (lines 37, 48) calls `opts.qc.invalidateQueries({ queryKey: ['feed'] })` using a raw string literal rather than `feedKeys.all`. The same raw `['feed']` literal appears in `feedHandlers.ts` (lines 18-19). | `src/hooks/sse/lockHandlers.ts:37,48` / `src/hooks/sse/feedHandlers.ts:18` | Low; import and use `feedKeys.all` for consistency. |
| FE-7 | Low | useReferencesState — `hydrated` return value is stale | The returned `hydrated: hydratedRef.current` (line 122) is read at render time from a ref, so callers receive the value that was current at the last render, not a reactive signal. In practice `AnnotateDoc` uses `hydrated` only as a guard in `canEdit` / button disabled logic through `refs.list` (which IS reactive), so there is no actual UI regression — but the `hydrated` field on the return object is misleading as a "reactive boolean". | `src/hooks/useReferencesState.ts:122` | Info — no bug, but the field name implies reactivity it does not have. |
